# 以虎 One · 应用接入规范

> 版本 v1 · 2026-10-10
> 适用：所有要接到以虎 One 上的东西——代码应用、已有系统、轻应用、AI 助手、Skill，不论是以虎内部、客户还是外部开发者做的。
> 本文只列**规则**；怎么做见每节末尾链接的开发中心文档（跑起来的平台上是 `/dev/<名称>`，仓库里是 `console/docs/devcenter/<名称>.md`）。
> 用词：**必须** = 不满足不能上线；**建议** = 不满足能上线但体验或维护会受影响。

## 1. 选哪种接入方式

| 你要接的是 | 用 | 谁能发布 | 审核 |
| --- | --- | --- | --- |
| 要自己后端、数据库的正式系统 | **代码应用**：Git 仓库，跑在平台上 | 管理员、开发者 | 每次提交都审 |
| 已经部署在别处的系统 | **外部应用**：登记地址，接统一登录；现成产品走标准 OIDC | 所有人 | 分享、上架时审 |
| 登记、报名、看板之类的小工具 | **轻应用**：对话生成的单页面，跑在浏览器沙箱里 | 所有人 | 上架时审 |
| 专门做某件事的 AI | **AI 助手**：提示词 + 工具 + 模型 | 所有人 | 上架时审 |
| 教 Agent 怎么做事的「做法」 | **Skill**：含 `SKILL.md` 的文件夹，装到各自的 Agent 里 | 所有人 | 上架时审 |

谁能看到、能用，只由「发布范围 + 可见范围」决定（仅自己 / 指定同事或部门 / 上架全公司），平台所有入口（工作台、市场、AI 工具、统一登录、MCP）判断一致。

## 2. 接入等级

| 级别 | 做到什么 | 要求 |
| --- | --- | --- |
| L1 部署 | 跑在平台上，出现在工作台 | 代码应用**必须** |
| L2 统一认证 | 用平台身份登录 | 所有有登录的应用**必须** |
| L3 使用数据 | 上报谁在用、做了什么 | **必须** |
| L4 AI | 提供 MCP 工具，AI 助手能操作 | 建议 |
| L5 大模型 | 应用的 AI 用平台托管的模型 | 建议（不要自己保管模型密钥） |

## 3. 必须遵守的规则

### 3.1 部署（代码应用）

1. 仓库根目录有 `Dockerfile` 和 `yh-app.json`；服务监听 `PORT`，日志打到标准输出；镜像能在 arm64 上运行
2. `/health` 免登录返回 200（上线、自动发布、回滚都靠它）
3. `yh-app.json` 的 `code` 一旦定了**不能改**（决定地址、容器名、数据库名）
4. `yh-app.json` 必须带 `version` 字段（语义化版本，如 `1.0.0`），每次发版同步更新；平台安装时校验，缺失不能装（存量应用更新时提醒补上）；版本号显示在控制台「管理 → 应用」
5. 应用挂在 `<平台地址>/apps/<code>/` 下：浏览器会请求的地址（`fetch`、链接、表单、跳转）用相对路径，会话 cookie 限定在自己的路径
6. 数据只写两个地方：`DATABASE_URL` 指向的库、`/data` 目录
7. 密钥不进代码、清单、Dockerfile、前端；需要的密钥由管理员写进服务器上的 `apps/<code>/.env`
8. 应用之间不直接互访（网络是隔离的）；要协作，经平台 MCP

→ [应用部署规范](../console/docs/devcenter/deploy.md)

### 3.2 身份与权限

1. 登录只走平台统一认证（平台 SDK，或标准 OAuth2 / OIDC），**不自己维护账号密码**
2. `client_secret` 只在服务端；回调**必须**校验 `state`；登记的回调地址只含自己的域名
3. 用户主键用平台的 `user.id`（OIDC 里是 `sub`），不用姓名、工号、手机号当主键
4. 平台只告诉你「他是谁」，「他能做什么」由应用自己判断；没配置过权限的人默认最小权限
5. 接口未登录返回 401（不要 302）；页面收到 401 重新走授权
6. 员工发布的应用只能拿到申请并经用户同意的信息：默认姓名、账号、角色；部门类（`org`）、联系方式类（`contact`）要申请。代码里按「字段可能没有」处理

→ [统一认证](../console/docs/devcenter/sso.md) · [现成系统接入（标准 OIDC）](../console/docs/devcenter/oidc.md) · [用户主数据](../console/docs/devcenter/users.md)

### 3.3 使用数据

1. 关键操作调用 `track()`，`action` 命名为「对象.动作」（如 `order.create`）
2. `detail` 里不放原文、手机号、身份证号、密码
3. 影响他人的配置修改要上报（谁改的、改成什么）
4. 平台断开时应用照常可用：上报失败只打日志，不影响业务

→ [使用数据](../console/docs/devcenter/usage.md)

### 3.4 AI 工具（MCP）

1. MCP 端点**必须**校验平台带来的 access_token，不允许匿名；工具一律以**当前用户的身份和权限**执行
2. 只读工具声明 `readOnlyHint: true`；会改数据的不声明（平台会让用户先确认）
3. 工具名动词开头、snake_case；`description` 和参数说明写清楚用途和什么时候用
4. 通过 MCP 做的操作也上报使用数据，并能区分来源（`via: "ai"`）
5. 平台不直接改应用的数据库——Agent 要改应用数据，只能经应用自己的 MCP 工具

→ [接入 AI 助手（MCP）](../console/docs/devcenter/mcp.md) · [接入大模型](../console/docs/devcenter/llm.md)

### 3.5 发布与回滚

1. 在 `main` 开发；只用 `release.sh` 把通过测试的 `main` 推到 `release`，**不直接往 `release` 提交**
2. 平台跟踪 `release` 自动发布，健康检查不过自动回滚到上一版
3. 回滚只回代码不回数据库：表结构改动必须向前兼容（先加字段、后删字段）
4. `release.sh` 里的 `TEST_CMD` 必须是真实的测试命令

→ [应用部署规范 · 发布](../console/docs/devcenter/deploy.md) · [上线检查清单](../console/docs/devcenter/checklist.md)

### 3.6 轻应用

1. 轻应用是不可信代码，跑在沙箱 iframe 里：不能联网、拿不到登录凭证，只能用 `window.yh` 白名单里的能力
2. 数据存在平台、按应用隔离；私有记录只有自己可见，只能改自己创建的记录

→ [轻应用 SDK](../console/docs/devcenter/lite.md)

### 3.7 Skill

1. 根目录有 `SKILL.md`，frontmatter 写 `name`（小写字母、数字、短横线）和 `description`（做什么、什么时候用）
2. 不包含二进制可执行文件；不写入密码、API Key 等密钥
3. Skill 在使用者自己的 Agent 里执行：脚本不得上传数据、删除用户文件或做与说明无关的事（上架审核会逐个看文件）

→ [Skill 中心](../console/docs/devcenter/skills.md)

## 4. 平台给你的承诺

| 承诺 | 说明 |
| --- | --- |
| 接口兼容 | 平台 SDK 用到的接口（`/api/sso/*`、`/api/open/*`）和标准 OIDC 端点保持向后兼容；不兼容的变化提前在变更记录里写明 |
| 变化可查 | 影响接入的变化都记在 [变更记录](../console/docs/devcenter/changelog.md) |
| 隔离 | 每个应用独立网络、独立数据库账号；应用之间互相访问不到 |
| 不碰你的数据 | 平台不直接读写应用的数据库；备份会带上你的库和 `/data` |
| 失败可回 | 自动发布失败自动回滚，结果记在控制台并通知 |

## 5. 上线前

逐项过一遍 [上线检查清单](../console/docs/devcenter/checklist.md)（前四组必须），用普通用户、部门主管、管理员三种身份各走一遍。
