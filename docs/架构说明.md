# 以虎 One · 架构说明

## 边界：平台只做配置

| 平台（控制台）负责 | 应用负责 |
| --- | --- |
| 我是谁：用户、部门、登录方式（账号密码 / 钉钉 / 飞书 / 企业微信）、统一认证 | 他能做什么：应用内的角色和数据权限 |
| 有哪些应用、谁能看到、放在谁的工作台上 | 业务功能本身 |
| 用什么模型、AI 助手的规则 | 通过 MCP 暴露给 AI 的工具 |
| 应用怎么部署、发布、回滚、备份 | 自己的数据库表和 `/data` 文件 |
| 谁在用哪个应用（使用数据）、谁做了什么配置（审计） | 在关键操作处上报使用数据 |

判断一个功能该不该进控制台：**如果它只对某一类业务有意义（审批、考勤、采购……），它就是一个应用。**

## 应用市场

| 类型（App.kind） | 内容（AppVersion.payload） | 运行在哪 | 谁能发布 |
| --- | --- | --- | --- |
| AGENT AI 助手 | 提示词 + 工具名单 + 模型 | 控制台的助手运行时（`agent/runner.js` + `agents.js`） | 所有人 |
| LITE 轻应用 | 单文件 HTML | 浏览器沙箱 iframe（`LiteFrame.vue`），能力经 postMessage → `/api/lite/*` | 所有人 |
| EXTERNAL 外部应用 | 地址、回调、MCP | 别的服务器 | 所有人（分享要审核） |
| HOSTED 代码应用 | Git 仓库 | 平台容器（审核通过 → PlatformOp INSTALL → yh agent） | 管理员、开发者 |

- **版本与审核**：内容都在 `AppVersion` 里，`App.liveVersionId` 指向生效版本。发布范围 PRIVATE / SHARED / MARKET；`services/studio.js` 的 `needsReview` 决定要不要审核，`publishVersion` 让版本生效
- **可见性**：`apps.visibleTo`——发布者自己；SHARED 按 visibility；MARKET 要 `listed`（审核通过）再按 visibility。市场、工作台、AI 工具、统一登录、轻应用运行时都用它
- **AI 助手的工具** = 发布者选的 ∩ 当前用户能用的，以当前用户身份执行，写操作照样确认
- **轻应用沙箱**：`sandbox="allow-scripts allow-forms allow-modals"`（没有 allow-same-origin / popups / top-navigation）+ CSP 禁止一切网络；控制台只回应这个 iframe 的消息、只提供白名单方法；数据按应用隔离，私有记录只有自己可见，只能改自己创建的记录
- **授权确认**：非可信应用（员工发布的）第一次统一登录 / 打开要用 AI 或工具的轻应用时，用户确认，记在 `AppGrant`；申请变多重新确认。统一登录按 `org` / `contact` 收敛返回字段
- **空间（多公司 / 客户）**：人、部门、知识库属于一个空间，应用属于一个空间并可以分享给别的空间；`apps.visibleTo` 按「空间 → 组织 → 人」三段收敛，查人查部门按 `spaces.spaceWhere` 收敛，轻应用数据按写入者空间分开；统一登录带上用户所在空间。管理员跨空间。设计和二期见 [设计-多空间](设计-多空间.md)
- **隔离**：每个托管应用一个 Docker 网络 `yh-app-<code>`，只有 Caddy、控制台、MySQL、Redis 加入
- **应用独立域名**（`yh.env` 的 `APPS_URL`，生产应配）：代码应用只在应用域名下（`<APPS_URL>/apps/<code>/`），和控制台不同源，应用页面里的脚本读不到控制台的登录凭证（在 `localStorage`）；应用域名上没有控制台页面和接口，控制台域名下的 `/apps/*` 302 到应用域名。不配时应用和控制台同源（老模式）。路由由 `yh` 生成：`platform/caddy/apps/apps.site`（应用域名站点，只引入 `*.app`）+ `_apps-redirect.caddy`

## 组件

```
            ┌──────────── yh-caddy :80 ────────────┐
            │ /apps/<code>/*  → yh-<code>（剥前缀，带 X-Forwarded-Prefix）
            │ 其余            → yh-console:3105
            └───────────────────────────────────────┘
yh-console ── Prisma ──▶ yh-mysql / yh_console
   │  ▲
   │  │ /api/platform/*（PLATFORM_TOKEN）：登记应用、领取操作、交回日志、上报状态、发布记录
   │  └──────────────── yh agent（宿主机常驻，持有 Docker）
   │
   ├─ /api/sso/*      统一认证（OAuth2 授权码；应用 access_token 2 小时）
   ├─ /api/open/*     应用凭证（Basic）：用户主数据、使用数据
   ├─ /api/mcp        MCP 网关：通用工具 + 用户可见应用的 MCP 工具（带用户身份转发）
   └─ /api/assistant  内置 AI 助手（OpenAI 兼容 / Anthropic / OpenHex），写操作先出确认卡片
```

## 控制台 ↔ 宿主机

控制台容器没有 Docker 权限。管理员点「安装 / 发布 / 停用 / 重启 / 移除 / 日志」时：

1. 控制台写一条 `PlatformOp(PENDING)`（同一应用同时只能有一个未完成的操作）
2. `yh agent` 每 4 秒 `POST /api/platform/ops/claim` 领一条，在子 shell 里执行对应的 `yh` 命令，输出即日志
3. `POST /api/platform/ops/:id/finish?ok=` 交回结果和日志；界面轮询显示
4. agent 每 30 秒上报各应用运行状态（容器、健康检查、版本、内存），每 `WATCH_INTERVAL` 秒检查一轮 `release` 分支

agent 与手动 `yh update`、自动发布共用一把发布锁；领了任务超过 30 分钟没交回的算失败。

**平台自身的升级**走同一套机制，控制台不联网、不碰宿主机：

- 版本号在根目录 `VERSION`。从 Git 装的机器跟踪 `release` 分支自更新（`self_update`）；用更新包装的机器按版本号升级（`yh upgrade`）
- agent 每 30 秒把「当前版本、安装方式、查到的最新版本」报给控制台（`POST /api/platform/info`，存在 `SystemSetting` 的 `platformInfo`），概览页据此提示新版本；agent 在不在线也看这个上报
- 管理员点「升级」→ `PlatformOp(UPGRADE)` → agent 执行 `yh upgrade`：备份平台文件和控制台数据库 → 换文件 → 重建控制台，失败回滚。升级完 agent 发现 `VERSION` 变了，`exec` 成新版本的脚本
- 不能联网的机器：管理员上传更新包（存 `PlatformPackage`），agent 经 `GET /api/platform/packages/:id` 取走安装
- 平台的操作和发布记录记在保留名 `platform` 下（应用不能用这个 code）

## 数据模型

`User` / `Department` / `UserDept`（用户与组织）· `App` / `AppVersion` / `AppRating` / `AppReport` / `AppGrant` / `AppData` / `UserApp` / `SsoCode` / `ApiKey` / `AppUsageEvent`（应用、市场与统一认证）· `PlatformOp` / `DeployRecord` / `PlatformPackage`（平台运维与升级）· `LlmConfig` / `AgentConversation` / `AgentMessage` / `PendingAction`（AI）· `SystemSetting` / `AuditLog`（设置与审计）。见 `console/backend/prisma/schema.prisma`。

## 配置放哪

- 只有启动必需和安全底线放环境变量：`yh.env` → yh 生成 `platform/console.env`（数据库、JWT、加密密钥、平台令牌、访问地址、开发登录开关）
- 其余都在控制台里改、即时生效：`console/backend/src/services/settings.js` 的 `SCHEMA` 加字段，前端按 schema 自动渲染

## 外观（VI）与版本

- **VI 是一组设计令牌**（主色、强调色、底色、文字、边框、状态色、圆角、阴影、渐变、字体、导航样式），不是一个主色。`services/theme.js` 定义令牌和预设（默认「以虎科技 VI」，还有「经典蓝」）；存的是 `{ preset, tokens: 改过的项 }`，生效值 = 预设 + 改过的项
- 平台的 VI 在系统设置 `appearance.theme`；每个空间可以有自己的（`Space.brand`：名称、LOGO、主题），`/api/me` 的 `brand` 给空间里的人，`null` = 跟随平台
- 前端 `utils/theme.js` 的 `deriveVars` 把令牌展开成整组 `--yh-*`（和 Element Plus 的 `--el-*`）变量；组件样式只用这些变量。`styles/main.css` 的默认值就是对以虎 VI 跑 `deriveVars` 的结果
- 版本号 x.y.z（0.x = Beta）在根目录 `VERSION`，`scripts/bump-version.sh` 一处改全；所有登录用户在侧边栏 / 「关于」看到（`/api/me` 的 `platform`），见 [版本管理](版本管理.md)
