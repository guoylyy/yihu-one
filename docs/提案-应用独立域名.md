# 提案：应用独立域名（REQ-03）

> 状态：**已定 B 方案并实现**· 2026-10-10。现网切换步骤见 [发布方式](发布方式.md) 第 2 节 E
> 对应需求文档 REQ-03「发布规范化」里的「自动子域名分配」。REQ-03 其余几项（code 冲突检查与替代建议、名称 / 简介 / 图标由 Agent 提建议后用户确认）已经做了，见开发中心「用 Agent 发布」。

## 一、需求文档里的前提要更正

需求文档说「子域名目前要手工进 Caddy 证书白名单」。**现在的架构里应用没有子域名**：所有应用都挂在平台同一个域名下的 `/apps/<code>/`，加应用不需要碰证书和 DNS（这正是当初选路径路由的原因）。只有 `EXTRA_TUNNELS`（不归平台管的独立服务）用独立域名。

所以这件事不是「把手工配置自动化」，而是**要不要从路径路由改成域名路由**。

## 二、真正要改的理由：安全

路径路由下，**代码应用和控制台是同一个源**（同协议、同域名、同端口）。控制台把登录凭证（7 天有效，带这个人的全部权限，管理员就是管理员权限）存在浏览器的 `localStorage` 里，同源的页面都能读。

在本机测试实例上验证过：打开一个代码应用 `/apps/hello/`，页面里的脚本能直接读到控制台的登录凭证。也就是说，**任何一个代码应用的前端代码，都能拿到打开它的那个人的控制台身份**——包括管理员。

| 应用类型 | 受影响吗 |
| --- | --- |
| 代码应用（HOSTED） | **受影响**：和控制台同源 |
| 外部应用（EXTERNAL） | 不受影响：在别的域名 |
| 轻应用（LITE） | 不受影响：沙箱 iframe 没有 `allow-same-origin`，是独立的不透明源 |

现在能接受这个风险，是因为代码应用只有开发者能提交、每次都要管理员审核。但平台定位是「人人可创造、Agent 一句话发布」，代码应用会越来越多，审核看不住每一行前端代码。把凭证换成 Cookie 也不解决：同源页面照样能带着 Cookie 调控制台接口。**根本的办法是让应用和控制台不同源。**

## 三、三个方案

| | A. 每个应用一个子域名 | B. 所有应用一个独立域名（推荐先做） | C. 保持现状 |
| --- | --- | --- | --- |
| 地址 | `purchase.one.example.com` | `apps.one.example.com/apps/purchase/` | `one.example.com/apps/purchase/` |
| 控制台凭证暴露给应用 | 不会 | **不会** | 会 |
| 应用之间互相隔离（浏览器层面） | 是 | 否（和现在一样） | 否 |
| DNS | 泛解析 `*.one.example.com` | 多一条 `apps.one.example.com` | 不变 |
| 证书 | 云服务器 Caddy 按需签发（on-demand TLS + `ask` 校验），不用 DNS 接口 | 多一张固定证书 | 不变 |
| 隧道 | frpc 加泛域名 `*.one.example.com` | frpc 多一个域名 | 不变 |
| 应用要改代码吗 | **要**：各应用自带的 SDK 只认 `/apps/<code>` 形状的前缀，前缀变了要先升级 SDK | 不用（前缀照旧 `/apps/purchase`） | — |
| 改动量 | 中：`yh` 生成按 Host 路由、云端 Caddy 按需证书、`ask` 校验接口、回调地址迁移 | **小**：多一个域名的路由和证书，`/apps/*` 301 跳到新域名 | 无 |

**建议：先做 B，A 留给以后需要应用之间也隔离时再做。** B 用很小的改动就堵住了「应用拿到控制台身份」这个口子；A 的好处（应用之间隔离）现在不是刚需，代价是泛解析 + 按需签证书的运维面。

## 四、B 方案怎么落

1. **配置**：`yh.env` 加 `APPS_URL`（如 `https://apps.one.example.com`）。放 `yh.env` 而不是系统设置，是因为 Caddy 和隧道在控制台起来之前就要用它（和 `PUBLIC_URL` 一样）。**留空 = 保持现在的路径模式**，本机试用、测试实例不受影响
2. **入口**：平台机器的 `yh-caddy` 按 Host 分流——应用域名下只转发 `/apps/<code>/*` 给各应用容器（路径不变：实现时发现各应用自带的 SDK 只认这个形状的前缀）；控制台域名下的 `/apps/<code>/*` 302 跳到应用域名的同一路径（用 302 不用 301：301 会被浏览器一直缓存，以后回退会把人带去旧地址）
3. **隧道与证书**：`yh` 渲染 frpc 时把应用域名加进 `customDomains`；云服务器 Caddy 多一段站点配置——按现有 `cloud/install.sh` 的纪律：**先备份 → `caddy validate` → 原子 reload**，不硬重启
4. **应用**：`YH_APP_URL` 变成应用域名；统一登录的回调地址同时登记新旧两个，过渡期结束再去掉旧的
5. **控制台**：应用域名上**不提供**控制台页面和 `/api/*`（这一点是隔离成立的关键，要有自测）
6. **验证**：`tunnel-test.sh` 加应用域名的渲染检查；`selftest.sh` 加「应用页面读不到控制台凭证」「应用域名上访问 `/api/me` 被拒」两项

估计：1～2 天开发 + 一次现网切换（要在云服务器加 DNS 和证书）。

## 五、要拍板的

1. 做 A、B 还是 C？（建议 B）
2. 应用域名用什么？（如 `apps.one.example.com`）
3. 老地址 `/apps/<code>/` 跳转保留多久？（建议一直保留跳转）

在拍板之前，现状下能做的缓解：代码应用的审核要把前端代码也看一遍（有没有读 `localStorage`、有没有往别处发请求）；管理员尽量不用管理员账号打开没审过的代码应用。
